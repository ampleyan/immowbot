# SQLite-to-PostgreSQL Migration Design

## Goal

Prepare Immowbot to run exclusively on the existing `immotool` PostgreSQL database while safely importing an explicitly supplied SQLite database exactly once. Preserve all application data, IDs, relationships, and current behavior. SQLite remains an import source and rollback archive only; it is never a runtime fallback.

## Scope and safety boundary

This change does not contact `kodisrv`, install anything on the Pi, change platform or application secrets, import live data, or delete any SQLite database. Existing `data/buyer.db` remains untouched.

The existing PostgreSQL platform provides database `immotool`, runtime login role `immotool`, non-login schema owner `immotool_owner`, a Unix socket at `/var/run/postgresql`, and a TLS endpoint named `kodisrv`. The migration belongs in this repository; it does not alter the platform repository.

## Runtime configuration

`DATABASE_MODE` accepts only `local` or `remote`; an unset or invalid value is an error.

- `local` constructs a PostgreSQL connection through `DATABASE_SOCKET_DIR` (default `/var/run/postgresql`) to `DATABASE_NAME=immotool` and `DATABASE_USER=immotool`. It never supplies a host/IP address and therefore cannot fall back to TCP or SQLite.
- `remote` accepts a PostgreSQL DSN only when its host is `kodisrv`, database/user are `immotool`, `sslmode=verify-full`, and `sslrootcert` names an existing regular CA-certificate file. Missing, relaxed, or conflicting TLS settings are errors.
- Passwords are supplied through the process environment/driver connection parameters and are not logged. Configuration errors describe only field names and safe paths.

The production Compose configuration will mount the Pi PostgreSQL socket into the application container only for local mode. It will contain variable names and safe defaults, not secret values. Docker startup must fail if PostgreSQL configuration is invalid or unavailable.

## Database schema and access model

`migrations/001_initial.sql` is the versioned PostgreSQL baseline. It creates the current domain tables: `users`, `property_lists`, `list_items`, `property_notes`, `listing_workflow`, `listing_interactions`, `alerts`, `smart_lists`, `searches`, `runs`, `source_runs`, `listings`, and `listing_versions`.

The baseline preserves all current column names, unique constraints, check constraints, explicit primary-key values, foreign keys, and delete behavior. IDs use `BIGINT GENERATED BY DEFAULT AS IDENTITY` so the importer can preserve historical values and later advance sequences. Boolean flags use `BOOLEAN`, financial decimals use `NUMERIC`, timestamps use `TIMESTAMPTZ`, and JSON documents use `JSONB`. Indexes cover the existing lookup and join paths.

Migrations run as `immotool_owner` (through the existing platform-admin role and `SET ROLE` when applicable). The `immotool` runtime role receives only its existing DML/sequence privileges. The application never creates or repairs schema at startup.

`PropertyStore` becomes PostgreSQL-only and owns all SQL. It uses `%s` binds, `RETURNING id`, `ON CONFLICT DO NOTHING`, `string_agg`, and JSONB operators/casts. SQLite PRAGMAs, `sqlite3.Row`, `lastrowid`, `INSERT OR IGNORE`, `GROUP_CONCAT`, and `json_extract` are removed. API and dashboard run-history queries move into store methods; callers do not issue backend SQL.

## One-shot SQLite importer

`scripts/import_sqlite_to_postgres.py` requires `--sqlite-path` and `--postgres-dsn`. It has no implicit source, destination, or destructive mode.

Before importing, it rejects non-absolute paths, symlinks, non-regular SQLite input, unsafe archive directories, incomplete/unexpected SQLite schema, SQLite integrity-check failures, foreign-key failures, a target without the expected baseline, and a nonempty target. It obtains a PostgreSQL advisory lock so concurrent imports cannot proceed.

The importer first creates a content-addressed, uniquely named copy and manifest in the configured rollback-archive directory. Archive files and manifests are published atomically, mode `0444`, and never overwritten. The source SQLite file is opened read-only and is never modified or deleted. Archive deletion is a separate, explicit archive-maintenance command and may remove only regular archive artifacts older than 30 full days; it refuses symlinks and never targets SQLite sources.

After SQLite preflight, importer writes occur in a single PostgreSQL transaction: insert in dependency order with explicit IDs, validate every source/destination table row count, validate PostgreSQL foreign keys, reset identity sequences above imported maxima, then commit. A failed validation rolls back all target writes. Archive creation is intentionally outside the transaction because it is a recovery artifact and remains available after an import failure. Output contains counts and safe file names only; it never echoes DSNs or credentials.

## Data fidelity

The importer preserves users, searches, runs, source runs, listings, listing versions, alerts, property notes, property lists/list items, smart lists, workflow records, interactions, payload JSON, timestamps, and every existing primary key. It preserves relationships through original foreign-key values and validates them after import. Fields currently linked by natural keys (`source`, `source_listing_id`, and `user_id`) retain their exact values and uniqueness semantics.

SQLite timestamps are parsed as ISO-8601 and stored as equivalent UTC `TIMESTAMPTZ` values. Store result mapping serializes them back to ISO-8601 strings, retaining current API/UI behavior. SQLite JSON text is parsed before insertion as JSONB and mapped back consistently for Python consumers.

## Testing

Existing behavior tests are migrated to a disposable PostgreSQL test database, never `kodisrv`. A dedicated test Compose configuration creates a fresh isolated PostgreSQL service/database; test setup applies the baseline and teardown drops the test database/schema. Tests cover store behavior, API/dashboard query behavior, configuration validation, and no SQLite fallback.

Importer tests create disposable SQLite fixtures containing every domain table and representative IDs/relationships, then import into a disposable PostgreSQL target. They assert exact per-table counts, IDs, data and JSON fidelity, foreign keys, sequence advancement, archive permissions/immutability, minimum 30-day retention, transaction rollback, unsafe-path rejection, nonempty-target rejection, and DSN/credential non-disclosure.

## Operational migration sequence

1. Apply `001_initial.sql` to the empty `immotool` database as the schema owner.
2. Take an operator-controlled copy of the current SQLite file; retain the original unchanged.
3. Run the importer with explicit paths/DSN; inspect its safe validation report.
4. Point the application at `DATABASE_MODE=local`; verify application behavior and PostgreSQL backup coverage.
5. Retain the immutable SQLite rollback archive for at least 30 days. Rollback means changing application configuration back before any separate, explicitly authorized cleanup; neither the application nor importer deletes SQLite data.
